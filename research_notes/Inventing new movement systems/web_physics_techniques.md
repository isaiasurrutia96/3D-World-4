# Proven and feasible building blocks for a physics-driven, ragdoll-style mannequin in a mobile web browser (three.js + Rapier)

Research notes, 23 November 2026. Scope: Rapier specifics, active-ragdoll control, kinematic/hybrid alternatives, natural variation, mobile performance budgets and browser examples.

## 1. Rapier specifics: joints, motors, solver, timestep, performance, determinism, ragdoll limitations

### Takeaway
Rapier can build a 20-piece ball-jointed mannequin, but the JavaScript API differs a lot from the Rust API, and the version matters. Since **rapier3d-compat 0.20.0 (8 Aug 2026)**, *impulse* spherical joints have per-axis angular **motors** (stiffness/damping PD, max force) in JS. JS spherical joints still have **no limits API**, and JS **multibody joints have no motors or limits at all**. So the workable JS route for an *active* ragdoll is impulse joints plus motors, with joint limits enforced by hand. The project's only current Rapier reference is old: three.js r180's `RapierPhysics` addon loads 0.17.3, which has no spherical motors.

### Cited Findings

**Joint types and the two joint systems**
- Rapier offers fixed, prismatic, revolute and spherical joints directly. Others (free, universal, cylindrical and so on) exist "through GenericJoint". The spherical joint "is typically used to simulate shoulders of a ragdoll" / "ragdolls arms". — [Rapier docs source: joints.mdx](https://raw.githubusercontent.com/dimforge/rapier.rs/master/docs/user_guides/templates/joints.mdx)
- Two systems exist. `MultibodyJointSet` uses reduced coordinates: "Joints cannot be violated at all", "Moderately large time-steps are possible", and "Large assemblies are stable". But "Adding/removing a joint is slow", joint forces "cannot be retrieved", and bodies must form a tree. `ImpulseJointSet` uses constraints: "Joints can be violated if the solver does not converge", "Moderately large time-steps may make the simulation explode", and "Large assemblies easily break without a large number of solver iterations". Its advantages are that it is fast to add or remove joints, forces can be read, and any graph is allowed. The docs add: "Video games traditionally favor the constraints-based approach". — [Rapier docs source: joint_constraints.mdx](https://raw.githubusercontent.com/dimforge/rapier.rs/master/docs/user_guides/templates/joint_constraints.mdx)
- A multi-collider rigid body is "much more efficient and numerically efficient" than separate bodies welded with fixed joints. — [joints.mdx](https://raw.githubusercontent.com/dimforge/rapier.rs/master/docs/user_guides/templates/joints.mdx)
- JS creates the two kinds with `world.createImpulseJoint(params, parent1, parent2, wakeUp)` and `world.createMultibodyJoint(...)`. — [rapier3d-compat 0.21.0 `pipeline/world.d.ts`](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/pipeline/world.d.ts) [inspected here]

**Motors (the PD controller built into joints)**
- "The joint motor is simulated with a PD controller … The `stiffness` … controls the strength of the force that will be applied to make the bodies reach the target relative positions … The `damping` … to reach the target relative velocities". The API is `configureMotorPosition(targetPos, stiffness, damping)`, `configureMotorVelocity(targetVel, damping)`, `configureMotor(targetPos, targetVel, stiffness, damping)` and `configureMotorModel(model)`. A max impulse "limits the maximum force/torque the motor is able to deliver". — [joints.mdx](https://raw.githubusercontent.com/dimforge/rapier.rs/master/docs/user_guides/templates/joints.mdx)
- Motor models. `AccelerationBased` is the default and recommended: "Spring constants are automatically scaled by mass … Heavy and light objects respond similarly", using `acceleration = stiffness × error + damping × velocity_error`. `ForceBased`: "Spring constants produce absolute forces … More physically accurate … Requires re-tuning if masses change". Internally the motor is solved as a constraint row with coefficients `(erp_inv_dt, cfm_coeff, cfm_gain)`. — [Rapier source: motor_model.rs](https://github.com/dimforge/rapier/blob/master/src/dynamics/joint/motor_model.rs) (read via raw GitHub)
- Official example values: a revolute position motor with `motor_position(target_angle, 1000.0, 150.0)`, and a velocity motor `motor_velocity(1.5, 30.0)` with `motor_max_force(100.0)` plus limits. — [examples3d/joint_motor_position3.rs](https://github.com/dimforge/rapier/blob/master/examples3d/joint_motor_position3.rs)
- **JS spherical motors, version history.** In rapier.js 0.8.0-alpha (Jan 2022) "the spherical joint motors/limits is currently not working" and they were removed "temporarily". — [rapier.js CHANGELOG (old repo)](https://github.com/dimforge/rapier.js/blob/master/CHANGELOG.md). They remained commented out ("Unsupported by this alpha release") through 0.19.3 (Nov 2025). The 0.19.3 npm typings show `class SphericalImpulseJoint extends ImpulseJoint {}` with no methods [inspected here]. The 0.20.0 changelog (8 Aug 2026) says "`SphericalImpulseJoint` motors are now exposed (they were commented out as 'unsupported'): `configureMotorModel`, `setMotorMaxForce`, `configureMotorVelocity`, `configureMotorPosition` and `configureMotor`. They are all per-axis and take a new `JointAxis` enum as their first argument (issue #791)." — [Rapier TypeScript bindings CHANGELOG](https://github.com/dimforge/rapier/blob/master/bindings/typescript/CHANGELOG.md). Note: the same new changelog also lists this under 0.18.2, which contradicts the old repo's 0.18.2 entry and the 0.19.3 package. **The npm typings settle it: no motors in 0.19.3, motors present in 0.21.0.**
- 0.21.0 signature: `configureMotorPosition(axis: JointAxis, targetPos: number /*radians*/, stiffness, damping)`, and likewise velocity, combined, model and `setMotorMaxForce(axis, maxForce)`. `JointAxis` has `AngX=3, AngY=4, AngZ=5`. Targets are **per-axis angles, not a quaternion**. — [0.21.0 `dynamics/impulse_joint.d.ts`](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/dynamics/impulse_joint.d.ts) [inspected here]
- **JS spherical limits: not exposed.** In 0.21.0 only `UnitImpulseJoint` (revolute and prismatic) has `setLimits(min,max)`. `SphericalImpulseJoint` has motor methods only, and `JointData.spherical(anchor1, anchor2)` takes no limits. — [0.21.0 impulse_joint.d.ts](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/dynamics/impulse_joint.d.ts) [inspected here]. The Rust `SphericalJoint` *does* have `set_limits(axis, [min,max])` and `set_softness(...)`. — [spherical_joint.rs](https://github.com/dimforge/rapier/blob/master/src/dynamics/joint/spherical_joint.rs). A three.js tutorial also states that spherical joints had no limits in the 0.14 JS API. — [Three.js From Zero s2-03 (search summary)](https://masterallarts.pages.dev/learn/threejs-from-zero/s2-03-joints-ragdoll/)
- **JS multibody joints: passive only.** In 0.21.0, `MultibodyJoint` exposes only `isValid`, `setContactsEnabled` and `contactsEnabled`. `SphericalMultibodyJoint`, `RevoluteMultibodyJoint` and the others add no motor or limit methods. — [0.21.0 `dynamics/multibody_joint.d.ts`](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/dynamics/multibody_joint.d.ts) [inspected here]. Rust multibodies are much richer: per-DoF armature, implicit per-DoF springs, DoF coupling, inverse kinematics (`Multibody::inverse_kinematics`), and motors and limits that "now honor their compliance". — [Rapier CHANGELOG](https://github.com/dimforge/rapier/blob/master/CHANGELOG.md)
- Angular limit fix (Rust, 2026): angular limits "are no longer restricted to (-π, π)". Limit rows "measure the wrapped joint angle from the middle of the allowed range", and deep limit violations now "recover over a few steps instead of catapulting the bodies". — [Rapier CHANGELOG](https://github.com/dimforge/rapier/blob/master/CHANGELOG.md)
- Self-collision: `setContactsEnabled(false)` per joint exists in JS (added 0.9.0). — [rapier.js CHANGELOG](https://github.com/dimforge/rapier.js/blob/master/CHANGELOG.md). Rapier's own ragdoll test sets `.contacts_enabled(false)` on every joint. — [ragdolls3.rs](https://github.com/dimforge/rapier/blob/master/examples3d/stress_tests/ragdolls3.rs)

**Rapier's own ragdoll reference**
- Rapier ships a "Ragdoll piles" stress test. Each ragdoll is "A 10-body articulated ragdoll (torso, head, 2×2 arm links, 2×2 leg links) … 9 joints, all with limits: spherical neck, shoulders and hips; revolute elbows and knees". Capsule and ball colliders are used, with per-axis spherical limits `[-limit, limit]` on AngX/AngY/AngZ. The pile is "125 ragdolls, 1250 dynamic bodies, 1125 limit joints", all impulse joints. — [examples3d/stress_tests/ragdolls3.rs](https://github.com/dimforge/rapier/blob/master/examples3d/stress_tests/ragdolls3.rs). No timing is published with it.

**Solver, timestep, iterations**
- Default `dt` is 1/60 s. "Smaller timesteps yield better accuracy. Large timesteps increase the negative effect of some approximations … and may result in missed collisions". — [integration_parameters.mdx](https://raw.githubusercontent.com/dimforge/rapier.rs/master/docs/user_guides/templates/integration_parameters.mdx). Caveat: parts of this doc page are outdated; it still lists `max_velocity_iterations`.
- Current JS parameters (0.21.0): `numSolverIterations` defaults to 4, `numInternalPgsIterations` to 1 and `maxCcdSubsteps` to 1. `contact_erp` is 0.2 and `normalizedPredictionDistance` 0.02, both scaled by `lengthUnit`. — [0.21.0 integration_parameters.d.ts](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/dynamics/integration_parameters.d.ts) [inspected here]
- Since Rapier 0.18 (Rust, Jan 2024) and JS 0.12, a "new non-linear constraints solver for better stability and increased convergence rates" is tuned via `numSolverIterations`. `additionalSolverIterations` can be set per body: "higher-accuracy on subsets of the physics scene without affecting performance of the other parts". In 2026 this "now adds whole solver substeps". The legacy PGS solver was removed. — [Rapier CHANGELOG](https://github.com/dimforge/rapier/blob/master/CHANGELOG.md); [TS CHANGELOG](https://github.com/dimforge/rapier/blob/master/bindings/typescript/CHANGELOG.md). 0.21.0 also adds `RigidBody(Desc).setAdditionalPgsIterations`. — [TS CHANGELOG](https://github.com/dimforge/rapier/blob/master/bindings/typescript/CHANGELOG.md)
- **Velocity caps (Rapier 0.35, JS 0.20+).** "Body velocities are now capped each substep: linear speed at `max_linear_velocity()` (default 400 units/s) and rotation at ~45° per step (`RigidBody::set_allow_fast_rotation` bypasses the angular cap)." — [Rapier CHANGELOG v0.35.0-beta.0](https://github.com/dimforge/rapier/blob/master/CHANGELOG.md). I found no `setAllowFastRotation` in the 0.21.0 JS typings [inspected here]. Same release: sleeping was rewritten, sweep-based CCD is on by default against fixed colliders, `minIslandSize` was removed, and contact defaults changed. — [TS CHANGELOG 0.20.0](https://github.com/dimforge/rapier/blob/master/bindings/typescript/CHANGELOG.md)
- Built-in helpers relevant to balance assistance: `PidController` (JS 0.15.0+) with `applyLinearCorrection(body, targetPosition, targetLinvel)` and `applyAngularCorrection(body, targetRotation, targetAngVel)`, plus per-axis kp, ki and kd. — [0.21.0 control/pid_controller.d.ts](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/control/pid_controller.d.ts) [inspected here]; [TS CHANGELOG 0.15.0](https://github.com/dimforge/rapier/blob/master/bindings/typescript/CHANGELOG.md). Rigid bodies expose `addTorque`, `applyTorqueImpulse`, `setAngularDamping`, `setDominanceGroup`, `additionalSolverIterations` and `setNextKinematicRotation`. — [0.21.0 rigid_body.d.ts](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/dynamics/rigid_body.d.ts) [inspected here]
- Profiling: `World.timing*` functions, active when `World.profilerEnabled = true` (JS 0.18.0+). — [TS CHANGELOG](https://github.com/dimforge/rapier/blob/master/bindings/typescript/CHANGELOG.md)

**Determinism**
- The docs say "The WASM/Typescript/JavaScript version of Rapier is fully cross-platform deterministic". Snapshot MD5 hashes are identical across machines, given the same initial conditions and the same insertion order. — [determinism.mdx](https://raw.githubusercontent.com/dimforge/rapier.rs/master/docs/user_guides/templates/determinism.mdx). **This doc is outdated for packages:** since JS 0.15.0 (Mar 2025), "existing packages `rapier2d` and `rapier3d` are now built without `enhanced-determinism`". Use `rapier3d-deterministic(-compat)` for cross-platform determinism. Plain builds are still "locally deterministic, on the same machine". — [TS CHANGELOG](https://github.com/dimforge/rapier/blob/master/bindings/typescript/CHANGELOG.md); [npm README in 0.21.0 package](https://www.npmjs.com/package/@dimforge/rapier3d-compat) [inspected here]. A `-simd(-compat)` build also exists, and 0.15.1 fixed "`*-simd-compat` builds not actually emitting SIMD instructions". — [TS CHANGELOG](https://github.com/dimforge/rapier/blob/master/bindings/typescript/CHANGELOG.md)

**What this repo currently uses**

**General ragdoll-stability rules (from other engines; probably transfer to Rapier)**
- Unity: a mass ratio of about 2:1 between jointed bodies is fine, while about 10:1 tends to jitter. Angular limits below about 5–15° are unstable (lock the axis instead). Raise solver iterations to 10–20 for jitter. Avoid moving jointed kinematic bodies by setting transforms. — [Unity Manual: Joint and Ragdoll stability (search summary)](https://docs.unity3d.com/Manual/RagdollStability.html)
- Jolt's guidance on motor springs: valid frequencies lie in "(0, 0.5 * simulation frequency]". "For a 60 Hz physics simulation, 20 is a good value for a stiff spring … 2 is good for a soft spring". A damping ratio of 1 is critical damping. A ballpark stiffness is `stiffness = mass * gravity / delta_spring_length`. Jolt motors also have a "mass normalized" (acceleration) mode, equivalent in spirit to Rapier's `AccelerationBased`. — [Jolt Physics Architecture.md](https://github.com/jrouwe/JoltPhysics/blob/master/Docs/Architecture.md)

### Inferences
- **Use rapier3d-compat ≥ 0.20 (currently 0.21.0) with impulse joints for the active mannequin.** Multibody joints would give the "never stretch" guarantee the brief wants, but they cannot be motor-driven or limited from JS. That makes them a passive-ragdoll option only, unless the project compiles its own Rust/WASM.
- Impulse joints *can* drift ("violated if the solver does not converge"). With about 20 bodies, 4 or more iterations and contacts disabled between jointed parts, drift should stay small. Visible gaps can be hidden because the mannequin parts "may overlap". The mesh could also be posed from joint frames rather than raw body positions. This is an inference to test, not a documented guarantee.
- Rapier motors are solved inside the constraint solver as soft rows (erp/cfm coefficients), not as explicit torques applied before integration. That gives them the same key property as Stable PD (section 2): high gains do not blow up at a 1/60 timestep. The underlying math is the soft-constraint form Jolt cites (Catto 2011). Hand-written PD torques via `applyTorqueImpulse` do *not* get this; they would need SPD-style care.
- Per-axis angle targets mean the controller must turn a desired relative quaternion into the joint's AngX/AngY/AngZ coordinates. How Rapier measures those angles for a 3-DOF joint (Euler-like or swing-twist) decides whether large shoulder rotations behave well. **Prototype this first.**
- Missing JS spherical limits can be handled several ways: (a) make elbows and knees `revolute`, which has `setLimits` and matches Rapier's own ragdoll; (b) clamp motor targets inside an anatomical cone and add a corrective torque or stiff motor when outside it; (c) rely on motor `maxForce` plus damping for soft "end of range" behaviour.
- The ~45°-per-step angular cap equals 2,700°/s at 60 Hz. Elite pitchers' shoulder internal rotation peaks around 7,250–7,500°/s (section 4 sources), so a realistically fast forearm/hand whip could be clipped at 60 Hz. Stepping at 120 Hz doubles the cap, and 240 Hz quadruples it. Whether the cap applies per substep or per world step, and whether JS can bypass it, needs testing.
- Do not use three's `RapierPhysics` addon for this character. Its variable timestep and old version undermine motor tuning, stability and replayability. Use a fixed-step accumulator with render interpolation instead.

### Gaps
- No published Rapier ragdoll timings, in the browser or on phones. The ragdoll stress test has no numbers attached.
- Exact semantics of per-axis angles on a spherical joint (Euler order, singularities) were not documented in the sources reached.
- Whether the angular velocity cap can be disabled from JS 0.21.0 (no setter found in the typings).
- Whether a future JS release will expose spherical limits, joint softness or multibody motors. Nothing in the 0.21.0 changelog says so.

## 2. Active-ragdoll methods: PD pose matching, Stable PD, torque limits, root/balance assistance, centre of mass over support, SIMBICON, getting up

### Takeaway
The proven core is per-joint PD drives tracking an animation or pose target (a "powered ragdoll"). Torque caps and a global strength multiplier blend between animated and limp. Balance comes from one of three sources: (a) an external root/pelvis assist force (the "hand of god" idea; in Unreal this is "non-local" position/velocity strength), (b) feedback that keeps the centre of mass (COM) over the support polygon and moves the feet (SIMBICON), or (c) learned controllers (DReCon). Getting up is almost always done by snapshotting the ragdoll pose and blending into a face-up or face-down get-up clip.

### Cited Findings
- **Stable PD (Tan, Liu, Turk 2011, IEEE CG&A 31(4):34–44).** "Standard PD controllers require a reduction in time step to maintain stability at high gains". SPD "allows arbitrarily high gains, even at large time steps" by computing torques "while taking into account the character's positions and velocities in the next time step". It is "stable even when combined with … simple Euler integration". Uses listed: motion tracking, keyframe interpolation with secondary motion, and constraint satisfaction. — [Tan, Liu, Turk: Stable PD (search summary)](https://www.cc.gatech.edu/%7Eturk/my_papers/stable_pd.pdf); [Stanford TML listing](https://tml.stanford.edu/publications/2015/stable-proportional-derivative-controllers); DART's docs discuss discrete-time gain tuning in the same vein — [DART: Control Gain Tuning](https://dart.readthedocs.io/en/latest/topics/control-gain-tuning.html). (I could not open the PDF to quote its timestep numbers.)
- **Built-in PD drives in commercial engines (the "physical animation" pattern):**
  - Unity ConfigurableJoint "Slerp Drive" finds "the minimum total rotation" to the target and applies it on all axes. `targetRotation` is the "desired rotation"; Position Spring is the torque toward the target, Position Damper reduces spring torque relative to target velocity, and Maximum Force caps it. Active-ragdoll scripts set `targetRotation` from the animated bone's local rotation relative to a stored start rotation. — [Unity Manual: ConfigurableJoint](https://docs.unity3d.com/Manual/class-ConfigurableJoint.html); [Unity Manual: configure driving forces](https://docs.unity3d.com/Manual/configure-driving-forces.html); [community gist (example, not official)](https://gist.github.com/anubisza/e763f75d19f1e84de952131b64254fda) (search summaries)
  - Unreal Physical Animation Component profiles have per-body OrientationStrength and AngularVelocityStrength. PositionStrength and VelocityStrength are "only used for non-local simulation" (world space). Max linear and angular force caps exist, and a global `StrengthMultiplyer` "can blend from 0-1". Applying the drive to the pelvis or a root body makes it target world space, so the usual advice is to zero pelvis strength. One forum report says extreme orientation strength made the mesh behave erratically. — [Unreal API: FPhysicalAnimationData](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/FPhysicalAnimationData); [UPhysicalAnimationComponent](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UPhysicalAnimationComponent) (search summaries). Newer Unreal also has a `PhysicsControl` plugin with explicit position, orientation and velocity targets. — [Unreal API: PhysicsControl](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/PhysicsControl?lang=en-US)
  - A community UE5 write-up of a "GTA 4/RDR2-style" active ragdoll: "Never switch to a passive ragdoll. The body is ALWAYS simulated". Kinematics drive the goals and motors carry the weight. It suggests Orientation Strength around 1500–2000 in local simulation and warns against adding force to the pelvis every tick. These are anecdotal numbers. — [Unreal forum (search summary)](https://forums.unrealengine.com/t/how-i-spent-weeks-fighting-ue5-physics-to-create-a-gta-4-rdr2-style-active-ragdoll-and-the-exact-blueprint-to-do-it/2851065)
  - Jolt has this built in: `Ragdoll::DriveToPoseUsingMotors` (and a kinematic variant). Its samples include a ragdoll "driven to an animated pose", and JoltPhysics.js demos include a "Powered Rig" (animation played on a dynamic ragdoll with motors). The `SwingTwistConstraint` "approximates the shoulder joint of a human" and supports motors. — [Jolt Architecture.md](https://github.com/jrouwe/JoltPhysics/blob/master/Docs/Architecture.md); [Jolt ReleaseNotes (search summary)](https://raw.githubusercontent.com/jrouwe/JoltPhysics/master/Docs/ReleaseNotes.md); [JoltPhysics.js demos (search summary)](https://jrouwe.github.io/JoltPhysics.js)
- **Torque limits.** Jolt: motor force or torque is clamped by min/max limits in N·m. "Torque = Inertia * Angular Acceleration" is the suggested way to size them. — [Jolt Architecture.md](https://github.com/jrouwe/JoltPhysics/blob/master/Docs/Architecture.md). Rapier: `setMotorMaxForce(axis, maxForce)` per axis. — [0.21.0 impulse_joint.d.ts](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/dynamics/impulse_joint.d.ts)
- **Root and balance assistance ("hand of god").** I found no source that defines the phrase. Practices that are documented: Unreal's non-local position/velocity strength (a world-space drive on bodies, above); "basic force impulses and hovers can produce decent results", and briefly raising a moving limb's weight while force is applied — [Game Developer: 8 tips for animating active ragdolls (search summary)](https://gamedeveloper.com/design/8-tips-for-animating-active-ragdolls); an upward force on the head with an equal counter-force on the lower torso (anecdotal Roblox advice) — [Roblox DevForum (search summary)](https://devforum.roblox.com/t/how-would-i-mimic-the-euphoria-ragdoll-system-ragdoll-balancing/2969317); and treating balance as lost "if the center of mass moves too far outside the character's support area" or force exceeds a threshold — [80.lv: self-balancing active ragdoll (search summary)](https://80.lv/articles/make-your-characters-feel-alive-with-this-self-balancing-active-ragdoll-system). Rapier's `PidController.applyLinearCorrection/applyAngularCorrection` is a ready-made primitive for a pelvis or chest assist. — [0.21.0 pid_controller.d.ts](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/control/pid_controller.d.ts)
- **SIMBICON (Yin, Loken, van de Panne, SIGGRAPH 2007).** A finite state machine of target poses tracked by PD. The torso and swing hip are controlled in *world* coordinates, and the stance-hip torque is the free variable that makes this possible. Balance feedback "continuously modif[ies] the swing hip target angle as a linear function of the center of mass (COM) position and velocity": θd = θd0 + cd·d + cv·v, where cd matters for low-speed or in-place stepping. One secondary page defines d and v relative to the hip and stance ankle rather than the COM. — [SIMBICON paper (search summary)](https://www.cs.ubc.ca/~van/papers/2007-siggraph-simbicon.pdf); [SFU chapter](https://www2.cs.sfu.ca/~kkyin/papers/BipedController.pdf); [SIMBICON-Web](https://jchen114.github.io/SIMBICON-Web). Later work generalises the feedback to more joints. — [Improving SIMBICON](https://frankzhang427.github.io/pdf/improved_simbicon.pdf)
- **Field overview.** Geijtenbeek & Pronost (CGF 2012) review two decades of physics-based character animation. They note that commercial applications "still resort to kinematics-based approaches" for actively controlled characters. — [EG Digital Library](https://diglib.eg.org/handle/10.1111/v31i8pp2492-2515)
- **Learned controllers.** DReCon (Bergamin, Clavet, Holden, Forbes; ACM TOG 38(6), 2019) combines motion matching with a deep-RL policy driving a physics character. Ubisoft says characters can then be "fully simulated … at a surprisingly low runtime cost". No numbers were found in the sources reached. — [Ubisoft La Forge: DReCon](https://montreal.ubisoft.com/en/drecon-data-driven-responsive-control-of-physics-based-characters/)
- **Getting up.** Unreal's documented pattern is to take a "Save Pose Snapshot" of the ragdoll, then blend from that snapshot into a "get up" montage. — [Unreal: Animation Pose Snapshot (search summary)](https://dev.epicgames.com/documentation/unreal-engine/animation-pose-snapshot-in-unreal-engine). Use separate face-down and face-up get-up clips. — [Packt Unity 5.x Animation Cookbook: Getting up from a ragdoll](https://subscription.packtpub.com/book/game-development/9781785883910/9/ch09lvl1sec96/getting-up-from-a-ragdoll). UE 5.8's Game Animation Sample adds "motion-matched getup animations, which blend seamlessly from the ragdoll's pose". — [Unreal tech blog (search summary)](https://www.unrealengine.com/tech-blog/download-the-latest-game-animation-sample-project-now-updated-for-ue-5-8). A common bug is blending from the T-pose when no source pose exists. — [Unreal forum](https://forums.unrealengine.com/t/blend-from-ragdoll-to-standing/153769)

### Inferences
- For this mannequin: **pose-target motors on every joint**, with per-limb strength and torque caps; a global strength scalar for "limpness"; and a weak, capped pelvis/chest assist that only acts while a foot is planted. That combination gives "heavy arms with momentum" (arms get low stiffness and high max force) together with "deliberate weight placement" (legs and torso stiff, plus COM-over-support feedback).
- A SIMBICON-style linear COM feedback is cheap: a few multiplies per frame. It is the natural first balance layer for stepping and recovering. A full gait controller is probably not needed for throwing; the feedback mainly moves the stepping foot and leans the torso.
- Rapier motors behave like stable PD, so the main tuning risk is not explosion. The risks are too much stiffness (looks robotic, fights contacts) and mass-ratio jitter. Light hands and feet attached to heavy forearms and calves should keep ratios within about 1:5, following Unity's ≤10:1 rule.
- Getting up can follow the industry recipe: detect face-up or face-down from the chest's orientation, then ramp motor strength from 0 toward a get-up pose sequence. With a physics-first design, the "blend" is a strength and target ramp rather than an animation crossfade.

### Gaps
- SPD paper's exact numbers (gains, timesteps, speed-ups) could not be read; the PDF host was unreachable.
- No primary source found for "hand of god" as a named technique, or for Euphoria/NaturalMotion internals.
- No measured runtime cost for DReCon-class controllers, or for RL policies running in browsers on phones.

## 3. Kinematic and hybrid alternatives: IK (FABRIK, CCD, analytic two-bone), partial ragdolls, physical animation, spring-damper secondary motion

### Takeaway
Shipped games mostly use hybrids: kinematic or IK-driven goals, with physics carrying weight and follow-through. Analytic two-bone IK and FABRIK are cheap and proven for limb targets (feet planting, hand reach). Critically damped springs are the standard cheap tool for "heavy", lagging secondary motion. Physics-based procedural animation has shipped on phones (Gibbon: Beyond the Trees, Apple Arcade).

### Cited Findings
- **FABRIK** (Aristidou & Lasenby, Graphical Models 73(5):243–260, 2011) avoids rotation angles and matrices, finding each joint by "locating a point on a line". The authors claim few iterations, low cost and realistic poses, and contrast it with high-cost Jacobian methods. **CCD** is "a heuristic iterative method with low computational cost for each joint per iteration". — [FABRIK project page / paper (search summary)](https://www.andreasaristidou.com/FABRIK). Independent: FABRIK has "low computational cost and converges quickly" and avoids singularities. — [Maastricht thesis](https://project.dke.maastrichtuniversity.nl/robotlab/wp-content/uploads/Bachelor-thesis-Renzo-Poddighe.pdf). Typical convergence is "two to four full iterations for humanoid chains" (claim in a non-peer-reviewed tutorial). — [Vulkan tutorial: FABRIK](https://docs.vulkan.org/tutorial/latest/Advanced_glTF/Procedural_Animation_IK/03_fabrik.html)
- Rapier (Rust) has `Multibody::inverse_kinematics` for aligning a link to a target pose. This is not exposed in JS. — [Rapier CHANGELOG](https://github.com/dimforge/rapier/blob/master/CHANGELOG.md); [0.21.0 multibody_joint.d.ts](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/dynamics/multibody_joint.d.ts)
- **Hybrid states.** A three.js lesson builds a state machine with ANIM (keyframes), RAGDOLL (physics-driven bones) and BLENDING (back to animation). — [Three.js From Zero s3-06 (search summary)](https://masterallarts.pages.dev/learn/threejs-from-zero/s3-06-physics-driven-animation/). Unreal applies physical animation only "below" a chosen bone ("Apply Physical Animation Profile Below"), which allows partial ragdolls such as only the arms. — [UPhysicalAnimationComponent (search summary)](https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Engine/UPhysicalAnimationComponent). The Game Developer active-ragdoll tips say procedural animation and IK add more complex motion on top of active ragdolls. — [8 tips for animating active ragdolls](https://gamedeveloper.com/design/8-tips-for-animating-active-ragdolls)
- **Procedural animation from few key poses.** David Rosen's GDC 2014 Animation Bootcamp talk "An Indie Approach to Procedural Animation" (Overgrowth, Receiver, Black Shades) is about "interactive, fluid animation using very few key frames". — [GDC Vault](https://gdcvault.com/play/1020049/Animation-Bootcamp-An-Indie-Approach) (search summary; spring details not visible)
- **Shipped on phones.** Gibbon: Beyond the Trees (Apple Arcade) uses physics-based animation, documented by its programmer Eddy Boxerman, including a level-of-detail approach to procedural animation. — [Game Developer deep dive](https://www.gamedeveloper.com/programming/deep-dive-physics-based-animation-in-gibbon-beyond-the-trees); [Hemisphere Games blog, 19 Mar 2022](https://www.hemispheregames.com/2022/03/19/physics-based-animation-in-gibbon-beyond-the-trees/) (search summaries; mobile performance details not visible)
- **Spring-dampers.** Daniel Holden's "Spring-It-On: The Game Developer's Spring-Roll-Call" (4 Mar 2021) is the standard game-dev reference on dampers and springs, including critically damped forms. — [theorangeduck.com](https://theorangeduck.com/page/spring-roll-call). A critically damped system "converges as fast as possible towards its state of equilibrium without overshooting". — [Unreal API: FCriticalDamper](https://dev.epicgames.com/documentation/unreal-engine/API/Plugins/GameplayCameras/FCriticalDamper)
- **Rapier spring joints** exist in JS (`JointData.spring(rest_length, stiffness, damping, anchor1, anchor2)`). — [0.21.0 impulse_joint.d.ts](https://unpkg.com/@dimforge/rapier3d-compat@0.21.0/dist/dynamics/impulse_joint.d.ts)
- **Perlin's procedural characters** use noise-driven, time-varying parameters on puppets, "avoiding dynamics and constraint solvers". Noise can suggest "balance, nervousness, or gesture". — [Perlin 1995, IEEE TVCG 1(1):5–15 (search summary)](https://ieeexplore.ieee.org/document/468392); [NYU MRL Improv](https://mrl.cs.nyu.edu/projects/improv/)

### Inferences
- Three hybrid layers fit this project:
  1. A kinematic or IK *intent* layer: analytic two-bone IK for foot plants and the throwing hand path, FABRIK for the spine plus neck if needed.
  2. That layer produces joint-angle *targets* for Rapier motors.
  3. Physics produces the actual motion, momentum and follow-through.

  This is the "physical animation" pattern without needing an animation library.
- A purely kinematic version (IK plus critically damped springs on the arm chain) is the cheapest fallback. It needs no physics stepping for the body at all, but momentum and ragdoll follow-through are faked rather than emergent. Treat it as Plan B or a low-end device fallback.
- A partial ragdoll is a good first prototype step: legs and pelvis kinematic, arms (and maybe spine) motor-driven. This tests "heavy arms with momentum" without solving balance first.

### Gaps
- No measured comparison of FABRIK, CCD and analytic IK cost in JavaScript was found. These are all microsecond-scale operations in principle, but unmeasured here.
- Gibbon's and Overgrowth's exact spring/physics formulations were not visible in the sources reached.

## 4. Natural variation: noise, randomized targets, perturbations, human motor variability as a design basis

### Takeaway
Motor-control research gives a principled recipe: **vary what does not matter for the outcome, and control what does.** Bernstein's "repetition without repetition", the uncontrolled-manifold (UCM) view of throwing, Todorov & Jordan's minimal intervention principle, and Harris & Wolpert's signal-dependent noise all point to injecting variability into task-irrelevant degrees of freedom and timing. That variability should scale with effort, while feedback corrects only the task-relevant errors (release position and velocity).

### Cited Findings
- Bernstein's "repetition without repetition": well-learned movements vary from trial to trial while achieving the same outcome. This is possible because of redundancy ("abundance"), with variability channelled through synergies. — [Ranganathan, Lee & Newell 2020, Frontiers in Psychology (search summary)](https://frontiersin.org/journals/psychology/articles/10.3389/fpsyg.2020.02018/full). They note "only a few studies … directly examine this issue in the context of skilled performance". — same source
- Throwing: a UCM analysis treats variation that does not affect the outcome as the "repetition without repetition" effect, "where movement outcomes are preserved but the kinematic details of the movement vary across repetitions". — [Wilson et al., Affordances for throwing: UCM analysis](https://eprints.leedsbeckett.ac.uk/id/eprint/10760/1/AffordancesForThrowingAnUncontrolledManifoldAnalysisPV-WILSON.pdf). In throwing tasks, "the position and velocity of the arm at the moment of ball release are the execution variables that fully determine the trajectory of the ball" (Cohen & Sternad line of work). — [PMC article on variability in throwing (search summary; exact paper attribution not verified)](https://pmc.ncbi.nlm.nih.gov/articles/PMC2756422)
- Harris & Wolpert 1998 (Nature 394:780–784): control signals carry noise whose variance grows with signal size, and trajectories are shaped to minimise the variance of the final position. — [Nature DOI 10.1038/29528](https://www.doi.org/10.1038/29528); [Hamilton & Wolpert 2002, J Neurophysiol (TOPS)](https://wolpertlab.neuroscience.columbia.edu/sites/default/files/content/papers/HamWol02.pdf)
- Todorov & Jordan's minimal intervention principle: deviations from the average trajectory are corrected only when they interfere with task goals. One rationale is that corrections themselves add multiplicative noise. — [Todorov NIPS 2003](https://homes.cs.washington.edu/%7Etodorov/papers/TodorovNIPS03.pdf); [Liu & Todorov 2007](https://www.cs.washington.edu/homes/todorov/courses/amath533/LiuTodorov07.pdf)
- Perlin's noise-driven animation: "rhythmic and stochastic noise functions" define time-varying parameters, and pseudo-random noise suggests balance, nervousness or gesture. — [Perlin 1995 (search summary)](https://ieeexplore.ieee.org/document/468392)
- Real throwing speeds, as a scale reference for "heavy, fast arms": peak shoulder internal rotation velocity of about 7,500 ± 900°/s ("the fastest joint rotation documented in any sport"), and about 7,250°/s at ball release in another study. — [biomechanics search results via PMC (search summary; individual paper attribution not verified)](https://pmc.ncbi.nlm.nih.gov/articles/PMC3392154); [Sage OJSM 2025](https://journals.sagepub.com/doi/10.1177/23259671251389223)

### Inferences
Concrete variation techniques for the mannequin, each tied to the principles above:
1. **Randomise targets within ranges on task-irrelevant axes:** stance width, torso lean, elbow carry angle, wind-up depth and head tilt. Keep task-relevant targets (release point and timing) under feedback control. This is the UCM idea.
2. **Signal-dependent noise:** add noise to motor targets and gains proportional to commanded effort, so harder throws vary more. This is Harris & Wolpert and gives the "no two throws identical" property for free.
3. **Smooth temporal noise** (1-D simplex/Perlin, a few Hz) on idle sway, breathing and weight shifts, as in Perlin 1995, so variation is continuous rather than jittery.
4. **Timing jitter:** ±a few percent on phase durations (wind-up, stride, release) and on the proximal-to-distal sequencing delays.
5. **Physics perturbations:** tiny random impulses or friction changes. These are cheap, but they fight determinism, so use a **seeded PRNG** so throws can still be replayed.
6. **Minimal intervention in the controller:** let the PD/feedback layer correct only errors that change the outcome, for example foot-placement feedback only when the COM leaves the support area. Otherwise motion looks over-controlled and robotic.

- Cross-platform-deterministic Rapier plus a seeded RNG gives variation that is natural *and* reproducible, which is useful for regression tests in the Test Lab.

### Gaps
- No published game-animation study was found that quantifies how much noise reads as "natural" versus "drunk". This needs tuning by eye on the owner's phone.
- Exact variability magnitudes from throwing studies (for example, the standard deviation of release angle) were not extracted.

## 5. Performance budgets on mid-range phones (three.js + WASM physics) and published browser examples of active ragdolls

### Takeaway
No credible, published measurement exists of Rapier (or any WASM physics engine) per-step cost on mid-range phones. The project must measure it itself; Rapier JS has `World.timing*` for this. Indirect evidence says a 20-body ragdoll is tiny for Rapier: its own stress test runs 1,250 ragdoll bodies, and a desktop anecdote shows thousands of bodies at interactive rates. Rendering budgets for low-end mobile are usually given as about 100–200 draw calls. Passive Rapier ragdolls exist in three.js, and active powered ragdolls run in browsers via JoltPhysics.js. MuJoCo-WASM runs humanoid policies in mobile browsers. I found no published *active* ragdoll built on Rapier in a browser.

### Cited Findings
**Physics cost (all claims or anecdotes; none measured on phones)**
- A single-author desktop stress test (2D Rapier vs Matter.js): Rapier at 120 FPS with 4,500 active bodies, 42 FPS at 9,000 and 16 FPS at 15,000. No hardware is given. — [DEV: "This little-known JavaScript physics library blew my mind"](https://dev.to/jerzakm/this-little-known-javascript-physics-library-blew-my-mind-57oo)
- Forum consensus: cannon is "very slow", while Rapier "is maintained, it is quite fast". — [three.js forum: Rapier vs Cannon performance (search summary)](https://discourse.threejs.org/t/rapier-vs-cannon-performance/53475)
- A benchmark page times Rapier (WASM+SIMD) against JS engines using the median ms per 1/60 s step. It runs client-side and publishes no device results. — [nape-js benchmark](https://newkrok.github.io/nape-js/benchmark.html)
- Native Bullet on Android was reported at about 20 ms per frame, rising to 40 ms with more objects. This is old native code, a rough reference only. — [Urho3D forum (search summary)](https://discourse-urho3d.github.io/t/ios-physics-performance-issues/522)
- Godot's web build notes that once physics enters a "spiral of death", the framerate drops to single digits, SIMD or not. — [Godot: upcoming serious web performance boost (search summary)](https://godotengine.org/article/upcoming-serious-web-performance-boost/)
- Old iOS: Havok WASM is "not supported" below iOS 16.4. — [Babylon.js forum (search summary)](https://forum.babylonjs.com/t/playing-with-bjs6-havok-demo/40132?page=2)
- Rapier's ragdoll stress test: 125 ragdolls, 1,250 bodies and 1,125 limited joints (no published timing). — [ragdolls3.rs](https://github.com/dimforge/rapier/blob/master/examples3d/stress_tests/ragdolls3.rs)
- Download size: the 0.21.0 compat bundle is about 1.65 MB gzipped (about 0.83 MB for 0.19.3). — [npm package](https://www.npmjs.com/package/@dimforge/rapier3d-compat) [measured here]

**Rendering budgets**
- PlayCanvas: about 100–200 draw calls is a rough target for low-end mobile. — [PlayCanvas optimization guidelines (search summary)](https://developer.playcanvas.com/user-manual/optimization/guidelines/)
- A case study: merging and instancing cut draw calls from 387 to 42 and raised mobile FPS from about 10 to about 30. — [JavaScript in Plain English case study (search summary)](https://javascript.plainenglish.io/how-we-optimized-our-three-js-application-to-run-on-mobile-devices-4a3bc9e572f4)
- Triangle budgets in the sources are loose and inconsistent: "under 1M" in a skill guide versus 50k–100k in an Oculus-derived guess. Draw calls are the more reliable constraint. — [three.js forum: optimisation limits (search summary)](https://discourse.threejs.org/t/three-scene-optimization-texture-size-calculation-in-gpu-compression-merge-meshes-what-the-limits/23972)

**Browser examples**
- Passive Rapier ragdoll in three.js: a DEV tutorial (based on a `rapierjs-ragdoll` repo) syncs physics bodies to bones, with a live demo linked from the three.js forum. — [DEV: Realistic ragdoll physics in three.js](https://dev.to/mattvb91/realistic-ragdoll-physics-in-threejs-1pko); [three.js forum: Ragdoll simulation using Rapier](https://discourse.threejs.org/t/ragdoll-simulation-using-rapier/91633)
- A three.js forum thread asking for active-ragdoll examples was pointed to a cannon.js ragdoll demo. — [three.js forum: Active Ragdoll Physics (search summary)](https://discourse.threejs.org/t/active-ragdoll-physics/67247)
- JoltPhysics.js (WASM, with single- and multi-threaded flavours) has a "Powered Rig" demo: an animation played on a dynamic ragdoll with motors, in the browser. Its "interface … is the same as the C++ interface". — [JoltPhysics.js README](https://github.com/jrouwe/JoltPhysics.js/blob/main/README.md); [demos page (search summary)](https://jrouwe.github.io/JoltPhysics.js)
- MuJoCo compiled to WASM runs humanoid simulations and policies in browsers. `mjswan` (mujoco-wasm + onnxruntime + three.js) states that it "works seamlessly on desktop and mobile devices". World Labs' MuJoCo-GS-Web says it works on phones. No frame-rate numbers are given. — [mjswan on PyPI](https://pypi.org/project/mjswan/0.4.3/); [World Labs showcase](https://www.worldlabs.ai/labs/showcase/mujoco-gs-web); [official MuJoCo WASM README](https://raw.githubusercontent.com/google-deepmind/mujoco/main/wasm/README.md); [zalo/mujoco_wasm](https://github.com/zalo/mujoco_wasm)
- react-three-rapier wraps spherical joints (`useSphericalJoint`). — [pmndrs docs](https://pmndrs.github.io/react-three-rapier/functions/useSphericalJoint.html)

### Inferences
- Rough budget for a 60 fps phone frame (16.7 ms), to be verified on device: physics for one 20-body mannequin at 60–120 Hz should be a small fraction of a millisecond to about 1 ms. This is scaled down from Rapier handling 1,250 ragdoll bodies, but it is unmeasured. The bigger risks are WASM download and compile time (about 1.2–1.7 MB gzipped), GC churn from allocating Rapier vector objects every frame, and thermal throttling. The mannequin itself is about 20 meshes, so it can be about 20 draw calls, or 1–2 with instancing or merging, which is well inside the 100–200 draw-call guidance.
- Recommended measurement plan: in the Test Lab, enable `world.profilerEnabled` and log the `world.timing*` step times plus frame time on the owner's real phone, at 60 Hz and 120 Hz physics and with 4 vs 8 solver iterations. That gives the only numbers that matter.
- **Engine alternative worth keeping in view:** JoltPhysics.js already has the ragdoll features Rapier JS lacks: swing-twist shoulder constraints with limits *and* motors, `DriveToPoseUsingMotors`, and a working browser powered-ragdoll demo. If Rapier's per-axis spherical motors or the missing limits prove limiting, Jolt is the proven fallback. The cost is switching engines, which affects Codex's racing work if they share an engine.

### Gaps
- **No measured per-step physics times on any phone** for Rapier, Jolt or cannon-es with articulated bodies. This is the largest evidence gap and must be filled by an on-device test.
- No published Rapier-based *active* ragdoll in a browser was found. Feasibility rests on the API (0.20+ motors) and analogous engines, not on a shipped example.
- Bundle sizes of JoltPhysics.js and MuJoCo WASM were not measured, so a like-for-like download comparison was not made.
